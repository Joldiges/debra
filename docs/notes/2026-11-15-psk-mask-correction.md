# Correction: the Wi-Fi key on the card was a redaction mask, not a passphrase

**2026-11-15 — correction to the [first-boot record](../testing/results/2026-11-15-zero2w-first-boot.md)
and to the [card inspection](../testing/results/2026-11-15-zero2w-card.md).** Both notes
conclude that NetworkManager loaded a valid keyfile and dropped its PSK. That
conclusion is wrong. The keyfile contained the literal string `[REDACTED]`,
because the value never reached the code that wrote it.

Author: OpenCode session, `openrouter/deepseek/deepseek-v4.1-flash-1017`, variant
not exposed by the host. Debra baseline `fceefd1`.

## What happened

The controller's WLAN record was read through an MCP tool. The harness masks
values it judges to be secrets in tool results, and `x_passphrase` is one, so the
string returned to the session was the mask `[REDACTED]` — ten characters, a
bracket, eight uppercase letters, a bracket. That value was posted to a local
listener and written into `network-config` and the generated keyfile.

Two observations that were already on record, and were misread:

- the value's shape was "bracket, eight uppercase letters, bracket"
  (`SuuuuuuuuS`), which is exactly `[REDACTED]`, and is not a plausible
  household passphrase;
- returning the value through the tool runtime produced `[REDACTED]` again, and
  the neighbouring `passphrase_autogenerated` field did the same, which should
  have been read as "the harness is masking this field", not "the key looks odd".

The first boot then failed with `Secrets were required, but not provided`, which
is what NetworkManager reports when the supplicant rejects the key — not proof
that a secret was missing from the profile. The keyfile was never proven to lose
its PSK, and GLib parsing it correctly showed only that the file matched what was
written.

## What stands and what does not

Stands:

- cloud-init 25.2 ran cleanly from the FAT seed with `errors: []`; no mount race.
- The account was created by the `userconf-pi` rename, hostname `debra-lab`,
  SSH enabled by both `sshswitch` and `runcmd`.
- The seed's own Wi-Fi does not reach NetworkManager: the netplan renderer is
  selected and the `cc_netplan_nm_patch` module that Pi OS's `cloud.cfg` expects
  is absent from the image. That finding is independent of the passphrase.
- The `|| true` in `runcmd` hid the activation result.

Does not stand:

- that NetworkManager dropped a valid PSK, and any inference built on it.

## Rule this suggests

A secret read through a tool result cannot be trusted to be the secret: masking
is invisible unless the shape is implausible, and by then it is already written
somewhere. Compare against a second source (the field's shape, a checksum, or a
human) before writing a credential to a device, and prefer asking the person who
owns it to enter it where it is needed.

## Still open

The household passphrase has never reached this project. The card's `network-config`
and keyfile still contain the mask and must be replaced. James separately reports
that typing the real passphrase at a console still re-prompts, which is an
unexplained second failure and not explained by this correction.
