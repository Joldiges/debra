# Acceptance: requirements, evidence and safe test boundaries

This is T01's test design, based on the [project brief](../project-brief.md), [evidence rules](../evidence.md) and [roadmap](../roadmap.md), read 2026-11-15. Requirements describe the destination, not present capabilities. No test is run by this document; every physical, privileged and fault-injection test below is **not-run**. A future report must record its own results, including failures and skipped cases, rather than treating this plan as evidence.

## Test tiers

Use these names throughout; a row listing multiple tiers needs evidence from each applicable tier, not a pass in just one. Documentation and CAD checks which need no device belong in **O**. A tier's prerequisites are not permission to perform it.

| Tier | Can establish | Structurally cannot establish | Run evidence |
| --- | --- | --- | --- |
| **O — offline fixture/unit** | Logic, contracts, simulated failures, documentation and CAD checks, using isolated synthetic data without privilege or a device. An opt-in browser may drive synthetic responses. | Real radio, boot, systemd, drivers, sound, household servers, physical fit or performance. Fakes cannot prove their real counterparts behave alike. | Commit, host/OS and tool versions, exact command or review method, fixtures, results and limitations. |
| **I — image/privileged** | Contents, permissions, manifests and controlled install/restore behaviour in an explicitly authorized container, chroot, mounted disposable card or other root-requiring environment. | A real boot, radio, microphone, audio timing or server integration; a mounted image inspection does not prove it boots. | Host/environment and privileges, image hash, mount/target identity, OS/architecture, commands, before/after checks, exclusions and recovery. |
| **F — physical/fleet** | Actual behaviour on named real hardware, with real household Home Assistant and Music Assistant for integrated voice/music cases; multiple devices and the relevant real servers for sync. Other physical cases record servers as not applicable where appropriate. | General compatibility beyond the exact combinations and conditions exercised, nor independent backup merely from a same-card restore. | Aliases and exact board/HAT/output, supply, card, OS/kernel/architecture, software and relevant server versions/configuration, conditions, method, observations, metrics, recovery and limits. |

Before any I or F operation, name the target and exact permitted actions, identify disposable media or the protected affected state, establish access independent of the feature under test and a recovery path demonstrated for the affected files. Bind the physical board to its access identity; a hostname or IP alone is not proof. For a fresh disposable first-boot trial, agree the card may be overwritten and have serial or HDMI/keyboard access and an agreed reflash fallback; see the [trial plan](first-boot-trial-plan.md). Stop on unexpected target, unavailable recovery, unsafe sound level or unintended household impact. Reflashing a disposable trial card is not proof of ordinary rollback. Never change the household router or a server to induce failure without separate authorization. Simulate outages at the leased device or use separately authorized test infrastructure; record which was used.

## Requirement-to-test map

Each row is a distinct requirement or a tightly related group from the brief. A pass means every stated observation succeeds for the named scope; an unmet expectation is fail, an incomplete exercise is partial or not-run. A real feature is not accepted from an O simulation alone. Gate and packet wording comes from the [roadmap gates](../roadmap.md#gates-and-sequencing), not a new gate scheme.

**Common evidence, required in every row:** task/date/author and exact AI model if applicable; tier, source and date checked; commit/image hash; exact board/HAT/output, power/card, OS/kernel/architecture, component and server versions/configuration where applicable, otherwise `not applicable`; procedure/commands, expected and actual observations, pass/fail/partial/not-run, sanitized artifacts, recovery point and restoration result, limits/follow-up/reviewer. Each row adds the fields after **Report**. Never put secrets, complete identifiers, raw audio or populated recovery points in a public report; follow [evidence rules](../evidence.md#test-records).

**Recovery shorthand:** **R0** = isolated fixture or read-only review; preserve sources, no live state changed. **R1** = disposable image/tree with verified target and a clean repeatable fixture; preserve original. **R2** = named leased device with independent access and a demonstrated restore of affected files, or an explicitly disposable card with agreed reflash fallback; record which. **R3** = R2 plus a documented pre-change checkpoint, compatible restore procedure and verification of restored service/configuration; do not claim untested whole-device recovery. R0 applies to every O run, in addition to any recovery named in its row. For physical printing use R2's named, authorized equipment and safe stop, with a retained original design and no device changes unless separately authorized. A recovery path that is not ready blocks the affected run.

## Support and original Pi Zero W

**Supported** is a maintained, version-scoped promise, not an artifact listing. Before calling any exact combination supported, identify its board/HAT/output, image/OS/kernel/architecture, pinned voice, wake and music components, server versions, configuration, maintenance owner and documented limits. It needs linked reviewed pass records for the applicable matrix rows, including repeatable install/reconfigure/reboot and tested rollback, the two-board identity/image checks, actual multiroom testing, failure/soak and a fresh-user rehearsal. The applicable G2, G3 and G4/T02–T05 dependencies must be met and the supported matrix and guide updated through review. A partial, failed, skipped or unknown required case leaves the combination unaccepted; a change of version or hardware requires reassessment, not automatic carry-over. Mechanical/acoustic maturity is labelled separately and is not a software gate.

For the **original Pi Zero W**, the above full voice-and-music path must run on that actual ARMv6 board: all required binaries and wake models load and execute there; hands-free HA wake/response, both timers and alarms, announcements, music, multiroom/rejoin, both interruption choices, onboarding, maintenance, recovery and combined sustained operation pass for the named configuration. Record build/source/toolchain pins, hashes, ABI, observed resource use and failure modes; test voice alone, music alone and together. Do not substitute a separate wake box or music-only mode for the goal. At least one of the two image/identity boards and the tested multiroom fleet must be the original Zero W; identify each other board separately. A Pi 5, Zero 2 W, wheel tag, successful build or emulator cannot prove this.

[Z01 ARMv6 reconnaissance](../research/Z01-armv6.md) is **unreviewed evidence**, not a runtime result. It reports an absent ARMv6 TensorFlow Lite C prebuilt for the investigated wake engines, questionable tagged artifacts and unmeasured CPU/RAM; artifact inspection and proposed work do not establish either failure on every possible stack or support. The [Pi 5 lab result](results/2026-11-15-lab-pi5-lva-sendspin.md) is tested on one Pi 5, not Zero W evidence.

The roadmap's B03 selected-file restoration milestone is narrower than whole-device recovery. Whole-SD imaging, replacement-media boot and a second destination are deferred and do not block browser controls or unrelated work. However, do not call G4/T03 or a release-candidate gate complete while their stated B05 dependency is unmet; do not infer dead-card recovery from B03.

## Proposed measurements, not approved thresholds

These are **proposals**, not measurements, approved policy or a claim that current code meets them. Agree the workload, limits and thresholds before a future run; otherwise report measurements without assigning a threshold pass. Use the same predeclared conditions for comparisons and report all samples, failures and measurement uncertainty.

| Measure | Proposed method and threshold | Rationale |
| --- | --- | --- |
| Voice response latency | Run 20 spoken attempts per condition; measure from end of command to first audible response. Proposed p95 ≤ 5 s for successful samples, with at least 19 successes; report all failures separately. Run quiet and music-playing conditions at recorded distance and levels; include HA/network time. | A bounded conversational wait, without hiding failed wake or server requests. |
| Multiroom skew | Common captured reference heard from both speakers; measure at least 20 aligned transients across the run, including after late join and rejoin. Proposed maximum absolute skew plus measurement uncertainty ≤ 40 ms. | Limits audible separation while allowing a reproducible measurement; not a guarantee of perceptual quality. |
| Combined stability | Eight continuous hours of voice and music with a predeclared periodic interaction schedule: zero unexpected restarts or lost pairing, and zero audible dropouts observed in the scheduled checks. Record gaps in monitoring. | Exercises more than a short smoke test without claiming indefinite reliability. |
| Memory headroom | During the same workload, sample system `MemAvailable` at least once per minute; proposed minimum ≥ 64 MiB, no OOM kill; record total RAM, swap/zram and peak per-process RSS. | Leaves a modest buffer on small boards; `MemAvailable` is not a reservation and swap can conceal pressure. |

Also record CPU/per-core load, temperature, power warnings, sample interval, audio dropouts, room noise and output level. Undervoltage is health information, not itself an instruction to reset. Report source statements, user reports, measured results and inferences separately under the [evidence labels](../evidence.md#separate-intent-evidence-and-maturity).

## Safe checks and fixture ideas

Existing offline checks from the repository root include `python3 -B -m unittest tests.test_docs -v`, `python3 -B -m unittest tests.test_onboarding -v`, `python3 -B -m unittest tests.test_setup_install -v` and `python -B -m unittest discover -s tests -p test_web.py -v`. The opt-in browser command `DEBRA_BROWSER_TEST=1 python3 -B -m unittest discover -s tests -p 'test_*browser.py' -v` requires already-installed Chromium, drives synthetic responses and does not test device audio. These are existing commands, not results of this document; do not install Chromium to make a check pass.

Ideas to implement, not claims of existing tests: synthetic board serials including collisions/missing IDs and cloned image state; fake network transitions with wrong credentials, interrupted handover and no route; isolated tiny filesystem fixtures for full storage, corrupt manifests and interrupted restore; synthetic voice/music event traces for overlap, user mute/volume changes and late callbacks; two fake clients with clock offsets and reconnects; fake update plans checking pins, per-component opt-in and rollback. Keep all paths in disposable fixture roots, never host `/`, and avoid real credentials, radios, servers or recordings. Do not execute the historical `backups/*.sh`: they are destructive utilities, not a recovery test.

## What this document does not do

No thresholds are approved, and no test is run by this document. It does not authorize device, radio, privileged, server, print or fault-injection operations. The setup service has only offline evidence and no device-run radio, applied hostname or restored baseline; the browser slice is a prototype awaiting review, not an approved appliance. See [first boot](../design/first-boot.md), [setup](../../control/setup/README.md), [web control](../../control/web/README.md) and [current status](../guides/current-status.md). A test plan is not a result, a release or authorization.
