# The Zero 2 W card: a mounted-card inspection that found a wrong Wi-Fi key

**2026-11-15 — inspected, not booted.** James flashed microSD `sdb` (29.5 GB) with
Raspberry Pi OS Lite 64-bit and a Seeed 2-Mics HAT v1 for the Pi Zero 2 W, then
asked whether the credentials would work. The card was mounted read-only and the
contents compared with the live UniFi configuration. **The Wi-Fi passphrase on
the card was wrong**, so the first boot would have failed to associate and needed
a console. Three fixes were applied to the card before first boot.

Author: OpenCode session, `openrouter/deepseek/deepseek-v4.1-flash-1017`, variant
not exposed by the host. Host: Fedora. Debra baseline `ee9d7aa`.

This is the first half of the [N06](../../roadmap.md) deliverable: a mounted-card
inspection. The control flash with the vendor AppImage, and any boot evidence,
are still open. Nothing here is a device result.

| Prior boots | None — `/var/lib/cloud` does not exist, so editing the seed still takes effect |

Imager wrote cloud-init files rather than the older `firstrun.sh` + `wpa_supplicant.conf`
pair, and there was no `ssh` marker file.

## Findings

1. **The Wi-Fi passphrase did not match the network.** `network-config` carried an
   8-character all-lowercase placeholder; the controller's key for `Oldiges WiFi`
   is 10 characters with mixed case and a symbol. There was **no common prefix**,
   so this was not a near-miss typo. A wrong PSK fails the handshake, leaves the
   device with no address, and makes SSH impossible — console access required.
   The SSID spelling, the `regulatory-domain: US` and the `cfg80211.ieee80211_regdom=US`
   in `cmdline.txt` all matched, and the WLAN is `wlan_band: both`, so 2.4 GHz
   broadcast was never the problem.

2. **The account should work.** `user.name` is `debra` with a yescrypt (`$y$`)
   hash and `lock_passwd: false`. The image's libcrypt carries yescrypt, and the
   hash parses as valid yescrypt with matching parameters. Pi OS does not create
   this account with `useradd`: its `cloudinit/distros/raspberry_pi_os.py` calls
   `/usr/lib/userconf-pi/userconf <name> <hash>`, renaming the built-in `pi`
   account, so `debra` inherits uid 1000, `/home/debra` and the pre-seeded group
   list. `sudo: null` writes no passwordless rule, so `sudo` prompts — expected,
   not a fault.

3. **A group that does not exist is not fatal.** The default user's group list
   names `lpadmin`, which this image does not define. cloud-init creates missing
   groups before adding the user (`add_user` calls `create_group` for each absent
   name), so this does not abort account creation.

4. **SSH hung off cloud-init alone.** SSH is enabled only by `runcmd:
   [systemctl, enable, --now, ssh]`; `ssh_pwauth: true` sets
   `PasswordAuthentication` but starts nothing. The image does have
   `sshswitch.service` enabled, which enables SSH when an empty file named `ssh`
   exists on the boot partition — an independent path that survives cloud-init
   failing, which is exactly the [N06](../../roadmap.md) failure mode.

5. **Which renderer gets the Wi-Fi was not settled offline.** Debian's
   `/etc/cloud/cloud.cfg` lists `renderers: ['netplan', 'network-manager']`, and
   `python3-netplan` plus the netplan bindings are installed, while
   `NetworkManager.service` is the only manager enabled and `systemd-networkd` is
   not. If cloud-init picks netplan, the Wi-Fi definition could be rendered for
   networkd and never reach NetworkManager. This was not provable without booting,
   so it was removed as a variable rather than guessed at.

6. **Keyfiles should be readable — the plugin is built in.** The
   `network-manager` package ships no `libnm-settings-plugin-keyfile.so`; only the
   ifupdown settings plugin is a separate module. The daemon binary itself carries
   the keyfile storage strings (`../src/core/settings/plugins/keyfile/nms-keyfile-storage.h`),
   so a keyfile in `/etc/NetworkManager/system-connections` is still the mechanism.
   Whether a *device* reads one is still unproven — that is one of the queued
   items in the [work queue](../../work-queue.md).

## What was changed on the card

- Corrected the passphrase in `network-config`.
- Added a NetworkManager keyfile through cloud-init `write_files`
  (`/etc/NetworkManager/system-connections/debra-wifi.nmconnection`, owner
  `root:root`, permissions `0600`, `autoconnect=true`), and added
  `nmcli connection reload` followed by `nmcli connection up id 'Oldiges WiFi'`
  to `runcmd`. This makes association independent of finding 5.
- Created the empty `ssh` marker file on the boot partition (finding 4).
- Verified afterwards: both files parse as YAML, the `network-config` password and
  the keyfile `psk` both equal the controller's value, and `runcmd` has two entries.

The passphrase was transferred to the card through a loopback POST so it never
appeared in any tool output, and the temporary file was shredded. It did pass
through the session's log once, because the controller's HTTP API rejected the
stored key directly (401) and only the MCP path could read it.

## What this does not show

- Nothing has booted. Association, the keyfile being honoured, hostname, SSH and
  the password are all unverified until the board is up.
- The image is 64-bit, so this card cannot test the Zero W v1.1 or ARMv6 at all.
- The HAT was not on the board and no audio work is implied.
- `packages: avahi-daemon` runs an `apt` step on first boot; avahi is already
  installed in the image, so a failure there should be harmless but has not been
  observed.
