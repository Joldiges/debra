## 16:0x — Code review: four state-machine defects, one restructure

WEB-REVIEW-04 accepted the rejection-persistence fix and found four more defects
in the browser state machine. All four came from one cause: a single `notice`
string and a single `unconfirmed` flag for two independent controls.

1. **HTTP 503 was treated as proof that nothing was applied.** The server returns
   503 when audio control is unavailable, including when a native command timed
   out *after* it may have run. The page said "not applied" and kept the error.
2. **A successful mute erased a volume rejection**, and a successful mute cleared
   volume uncertainty — unrelated evidence destroyed by an unrelated success.
3. **A pending write kept the pre-submission "not applied" label**, and an
   unavailable readback left it there indefinitely.
4. **Reconciling an old request discarded a newer preview**: submit 24 %, lose the
   response, move the slider to 50 %, and the next read of 24 % replaced the 50 %
   preview.

The fix is a restructure rather than four patches: `volumeOp` and `muteOp` are
separate records, each `pending`, `uncertain` or `rejected` with its own message;
`draft` now means only "the slider holds an unsubmitted value"; a definite
refusal is an HTTP status in a small set (400/401/403/404/405/413) and everything
else — including 503 and no answer — is uncertain until a readback agrees with it.
Reconciliation clears the draft only if the slider still equals what was
submitted.

### setup-r4: accepted defects repaired, every surviving mutation closed

`setup-r4` accepted the r3 repairs and asked for changes on eight new findings,

The three high findings were the kind that only show up in a real failure:

- **A reboot made the device permanently unusable.** A claim was a flag in the
  state file with no owner, so a power cut while joining left `connecting` with
  a claim set for ever. Every later submission was refused as busy, and each
  offline reboot repeated the sequence. The claim is now cleared on the boot
  that finds it, because a claim belongs to the process that set it, and a
  record that still says `connecting` is raised as a failure with its reason.
- **A failure could overwrite a success.** Settling the failure released
  ownership, then re-raised the access point outside the lock; a request
  admitted in that window could be overwritten by the older worker's full-state
  write, including a success. The rearm now happens under the admission lock,
  before ownership is released, and a worker that fails in any way it did not
  anticipate settles and releases instead of escaping its thread with a
  traceback that names a path.
- **The setup password could not be used twice.** It was regenerated on every
  raise, so reading it off the card and rebooting invalidated what had just been
  read, and one wrong household password replaced the credential the phone had
  saved. It is generated once and stored, and recorded *before* the access point
  is raised, so a failed state write cannot leave a live access point that no
  state describes.

### The seamlessness hole: nobody can get into the device page

Asked to look at the journey rather than the code, the user-facing gap is not a
missing feature in either service — it is the join between them. A person flashes
a card, the setup portal raises its own network, they join their Wi-Fi, and the
last screen tells them the device page is at `http://debra.local:8787/` and that
web control "may not be installed yet". If it is installed, the page asks for a
device access key, and the only documented way to get that key is to read
`~/.config/debra/web/access.key` in a private terminal on the device. The brief
explicitly rules a terminal out of ordinary setup, so the appliance's primary
path ends at a file the person cannot reach.

Two smaller facts make it worse rather than better. The web-control installer
does create the key when it prepares its own service, but nothing in the
card-preparation path installs web control: the setup service is a system unit,
the page is a user unit, and each installer knows only its own paths. And the
setup service's own credential — the password for its access point, carried on
the card — is unrelated to that key. Three credentials or none, depending on what
was installed, and no path between them.

[Browser enrollment](../design/browser-enrollment.md) sets out the four honest
answers and recommends one: **ask for the device password during setup**, on the
device's own network, before the join. That moment exists only behind the
card-carried setup-network password, so it adds no new trust boundary and no
unauthenticated window on the household LAN — which a first-run "claim" window
would. It also removes the 43-character key from the journey, which no one is
going to type into a phone correctly.

The note is deliberately not a decision: showing the generated key once on the
setup screen is a smaller change that removes the terminal today, and approving
from Home Assistant is the better multi-user answer later. What none of them
solve is stated too: plain HTTP on a home network, one shared credential with no
per-browser revocation, and a forgotten password with no recovery path that
does not say "re-flash the card".

**Unverified:** nothing was implemented. No credential store, no enrollment
screen, and no claim window exists; the device page still says the key exists and
that handing it over from setup is planned, because that is still true.

### Decided: the device password is chosen during setup

James chose the enrollment path: **the password is chosen during setup**, on the
device's own network, behind the card-carried setup-network password. Not a
displayed key, not a first-run claim window. The reasoning is in
[the design note](../design/browser-enrollment.md#the-decision).

He also asked for three development provisions: an explicit **bypass
authentication** switch, an **uncontested "forgot password"**, and `debra` as the
development password.

Those three are, on a shipped device, a complete takeover path — no credential, a
replaceable credential, and a public one. They are fine on a lab network and not
fine on a household one, so the note sets the boundaries rather than relying on
anyone remembering them: they are service modes and never defaults, the unit
template that installs the page must not carry them, `/api/status` reports which
mode is active so a script can prove it, an uncontested reset is loud in the
journal and on the page, `debra` fails the production length rule, and a named
test must fail if a production-mode server accepts `debra` or an unauthenticated
reset. The bypass itself needs no new mechanism: `--auth none` already exists and
already shows a banner.

Writing that down exposed the real blocker, which is not the review holding the
files. The web installer is a **user** unit installed into one account's home; the
setup service is a **system** unit that does not know which account that is. The
setup service therefore cannot write a credential the page will read. A prepared
image would settle it (I02), and until it does, this work is blocked on a
decision about the runtime account.

**Unverified:** nothing is implemented. No password form, no credential store, no
bypass button, and no reset path exists; the page still asks for the generated key
and still says handing it over from setup is planned.

### docs-r4: the acceptance design is accepted; Z01 still has three

Fourth round. `docs/testing/acceptance.md` came back **accepted** as reviewed
test-design evidence, five of eight findings closed and the three that concerned
that file closed. The reviewer's limits travel with it: it approves no threshold
and proves no capability, and every physical, privileged and fault-injection test
in it is still `not-run`. T01 is now `done` in the roadmap and its chain shows as
finished in the Todos view rather than waiting.

`Z01-armv6.md` came back **changes requested** for the third time, on three
points that were fair:

- The bubblewrap command I wrote bound the host emulator with `--bind` to
  `/usr/bin/qemu-arm-static` **inside** the image. Two defects in one line:
  `bwrap` creates a missing mountpoint only while its parent is writable, and
  after `--ro-bind /mnt/raspios /` that parent is read-only, so the command
  depended on a file the image may not have; and `--bind` leaves the host binary
  writable, which is not the read-only protection the experiment claims. It now
  puts a `tmpfs` on `/run` first — writable, so the mountpoint can be created —
  and binds the emulator there **read-only**, with the writable exceptions
  (`/run`, `/tmp`, `/dev`, `/proc`) named instead of implied.
- "A real armhf environment" was too loose. Debian's armhf baseline is ARMv7, so
  a Debian ARMv7 container satisfies that wording while exposing different
  compatible platform tags from Raspberry Pi OS on ARMv6 — and the tags are
  exactly what pip chooses by. The requirement is now an environment matching
  the target, with `sysconfig.get_platform()`, pip's compatible-tag list, the pip
  version and the index configuration recorded.
- The header claimed round 3 had closed "the browser/performance work". It had
  recorded the browser coverage as partly closed, with the contrast criterion
  open. The header now says what each round actually closed.

**Verified:** `tests.test_docs` and `tests.test_progress` pass, and the progress
generator refuses a packet marked `done` while its review row is still active —
which it did, until the T01 row moved to Accepted. **Unverified:** Z01's runtime
question is unchanged and unproven; nothing was executed; a fifth round is
needed, and the reviewer again could not verify the tree against the supplied
hash.

### code-r10: the browser slice is not accepted yet, and it was right

The r10 review came back **changes requested**, and the interesting part is that
every one of its blockers was real. Three suites passed (635 offline, 22
browser, 635 with the browser enabled), all eight historical survivors were now
killed — and the restore boundary was still incomplete, because killing the
reversals someone thought to write only proves those cases:

- `release_problem` skipped every argument that did not start with `/`. A
  marker-bearing unit whose command was `python3 not-installed/server.py serve`
  or `python3 -B -c 'print(1)'` therefore had **nothing to inspect** and restored
  with exit 0, printing that the release had been checked. Restore now requires
  the command shape `install()` writes — absolute interpreter, `-B`, the
  release's own `server.py`, `serve`, then known option/value pairs — and takes
  the release from that entry point instead of searching argv for something that
  looks like a path.
- The link check covered `web/` and `releases/` but not their ancestors. Renaming
  `~/.local/share` and pointing the name at a preserved copy repoints every
  release at once with every byte and digest inside unchanged, and restore
  published the previous unit through it. Every ancestor is now checked, which
  is the policy `install()` already applied.
- Four behaviour-changing mutations survived 183 web/setup/installer tests: the
  ancestor guard, a same-content link at `discovery.py`, a delegated `touchend`
  write on a planned control (the no-write sweep dispatched touch events only on
  labels), and an unconditional clear of the new session's in-flight Setup
  marker. Each now has a test that fails when the guard is removed — the last by
  holding **both** the old and the new Setup reads and releasing the old one
  first, which the supplied re-pair test could not see because it let the new
  read finish.

All six reversals were re-applied to a scratch copy and each died on its named
test. The README's claims were corrected at the same time: the marker is a
**format** check, not proof of authorship; "every read is bound to the session"
became "protected status and Setup reads", because the public pre-pairing device
inventory is deliberately not session-bound; and the restore boundary now
describes the command shape and the ancestor rule it actually enforces.

**Verified:** 675 offline tests pass (44 skipped), 23 browser tests pass, and
`tests.test_install`'s restore fixtures now install a real release instead of a
unit whose `ExecStart` was a single quoted word. **Unverified:** nothing was run
against systemd, a device or a real rollback; the ancestor rule also means a home
under a symlinked `/home` refuses restore, exactly as it already refuses install.
A fresh review (`code-r11`) is needed before this slice can be called accepted.
