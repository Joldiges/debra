## 16:0x — Code review: four state-machine defects, one restructure

WEB-REVIEW-04 accepted the rejection-persistence fix and found four more defects
in the browser state machine. All four came from one cause: a single `notice`
string and a single `unconfirmed` flag for two independent controls.

1. **HTTP 503 was treated as proof that nothing was applied.** The server returns
   503 when audio control is unavailable, including when a native command timed
   out *after* it may have run. The page said "not applied" and kept the error.
2. **A successful mute erased a volume rejection**, and a successful mute cleared
   volume uncertainty — unrelated evidence destroyed by an unrelated success.
3. **A pending write kept the pre-submission "not applied" label**, and an
   unavailable readback left it there indefinitely.
4. **Reconciling an old request discarded a newer preview**: submit 24 %, lose the
   response, move the slider to 50 %, and the next read of 24 % replaced the 50 %
   preview.

The fix is a restructure rather than four patches: `volumeOp` and `muteOp` are
separate records, each `pending`, `uncertain` or `rejected` with its own message;
`draft` now means only "the slider holds an unsubmitted value"; a definite
refusal is an HTTP status in a small set (400/401/403/404/405/413) and everything
else — including 503 and no answer — is uncertain until a readback agrees with it.
Reconciliation clears the draft only if the slider still equals what was
submitted.

### setup-r4: accepted defects repaired, every surviving mutation closed

`setup-r4` accepted the r3 repairs and asked for changes on eight new findings,
three of them high, plus six mutations that survived 24 deliberate breaks. It

The three high findings were the kind that only show up in a real failure:

- **A reboot made the device permanently unusable.** A claim was a flag in the
  state file with no owner, so a power cut while joining left `connecting` with
  a claim set for ever. Every later submission was refused as busy, and each
  offline reboot repeated the sequence. The claim is now cleared on the boot
  that finds it, because a claim belongs to the process that set it, and a
  record that still says `connecting` is raised as a failure with its reason.
- **A failure could overwrite a success.** Settling the failure released
  ownership, then re-raised the access point outside the lock; a request
  admitted in that window could be overwritten by the older worker's full-state
  write, including a success. The rearm now happens under the admission lock,
  before ownership is released, and a worker that fails in any way it did not
  anticipate settles and releases instead of escaping its thread with a
  traceback that names a path.
- **The setup password could not be used twice.** It was regenerated on every
  raise, so reading it off the card and rebooting invalidated what had just been
  read, and one wrong household password replaced the credential the phone had
  saved. It is generated once and stored, and recorded *before* the access point
  is raised, so a failed state write cannot leave a live access point that no
  state describes.

### setup-r5: accepted, narrow — and the four gaps it proved

### code-r8: two release blockers, and the tests that only looked like tests

`code-r8` said changes requested. The r7 safety work held — all three original
safety mutations are dead, cross-site switching works, and the request gate
still refuses what it should. But the documented rollback was broken, and three

**The rollback refused the installer's own units.** `--restore` split
`ExecStart` on whitespace and stripped double quotes, while the installer writes
systemd quoting with `%%` and `$$` for `%` and `$`. A HOME containing a space, a
percent or a dollar therefore produced a path that does not exist: the one
command a person is told to run after a bad upgrade failed on the generated
units it was meant to restore. Restore now decodes `ExecStart` the way systemd
quotes it, and the test builds a home whose path contains all three.

looked for the first literal `ExecStart` anywhere and checked one `server.py`.

files and still match the content address it is named by. The message and the
README separate "the file was restored" from "the service recovered"; only a
start that stays up can show the second.
