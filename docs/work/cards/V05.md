# V05 — stop-word setting and the Pi Zero W default

Read V05, V03, WEB05, the [web control design](../../design/web-control.md), the
page rule that a capability which does not exist is text rather than a disabled
control, and the dated [CPU accounting note](../../notes/2026-11-16-zero-w-lva-cpu-accounting.md).
No live device writes or service restarts without a named target, an approved
operation and a recorded recovery step.

## Bounded questions

Define one persisted setting ("stop word: enabled / disabled") with a per-board
default, and the inference gating it depends on. Establish: which configuration
object owns it and how it migrates; how a disabled stop word is reported without
implying the microphone is muted; what happens to an in-flight reply,
announcement or timer when the setting changes; and whether the Home Assistant
`active_wake_words` / stop-model contract in `satellite.py` is affected. Do not
add a second configuration authority beside C01, and do not duplicate WEB05's
board-aware presentation.

Also decide how the setting reaches the device: a pinned upstream LVA release
that contains the gating, or a scoped Debra patch with its own provenance and
tests. An unpatchable runtime must fail closed rather than silently lose the
saving.

## Acceptance

Return a setting contract (name, type, default per board revision, validation,
migration, atomic persistence), the runtime change it requires, and the
dashboard control with its offline test. Pi Zero W v1/v1.1 default is **off**;
every other board defaults **on** until measured. Report the CPU saving actually
measured on a named device, and the detection cost of enabling it. Mark every
device test `not-run` until a named device, authorized operation and recovery
exist. An unknown board revision must not silently inherit the Pi Zero W
default, and a disabled stop word must not be presented as microphone privacy.
